# Expert review of the upstream PR sequence

A skeptical-Fabric-reviewer pass over each PR in
`upstream-pr-sequence.md`, grounded in the fork's actual code. Verdicts:
**ship** (fine as scoped), **prep** (fine, but the PR must pre-answer a
known objection), **restructure** (the plan itself needs a change).

## The findings that change the plan

**1. Themes 3–4 have an undeclared facebook/react dependency — the
longest lead time in the sequence, and the doc doesn't mention it.**
The fork hand-edits the vendored renderer
(`Libraries/Renderer/implementations/ReactFabric-*.js`): a
`createTextNode` host-config path in `createTextInstance`, and the
removal of the "Text strings must be rendered within a \<Text>
component" validation. Upstream syncs those files from facebook/react
and does not accept hand-edits. Two consequences:

- The bare-strings-under-View capability (Theme 4's payoff) cannot ship
  at all without a React-side PR relaxing the parent-text validation
  behind a React Native feature flag, plus a renderer sync. The throw
  happens in the reconciler, before any host call — there is no C++
  workaround.
- The `#text` host-config path (PR 7) also lives in React. There is an
  interim RN-only wiring — keep the RawText protocol and intercept in
  `UIManager::createNode` (componentName `"RawText"` + flag → construct
  `#text`) — which lets Theme 3 land without waiting.

Restructure: add a **PR 0 / coordination workstream** — the facebook/react
PR (flagged host-config path + flagged validation relaxation) opened
*first*, since React-sync latency into RN is weeks. Re-scope PR 7 as the
C++ intercept; the host-config path becomes a follow-up that rides the
sync.

**2. `all: 'revert'` was spec-incorrect — FIXED in the fork.** `revert`
used to behave like `initial` at the native layer. Per css-cascade-4,
`revert` rolls back to the user-agent origin, and with no UA
declaration it falls through to unset — for inherited properties,
**inherit**. The fork now implements the correct resolution natively:
root `<Text>`'s UA `all: 'initial'` declaration moved from the JS
`uaStyle` merge to `ParagraphShadowNode`'s `UACascadeBoundary` trait
(the exact upstream design), `BaseViewProps` keeps the parsed keyword
verbatim (`initial`/`revert`/`unset`/`inherit`), and
`isInheritanceBoundary(bool uaDeclaresBoundary)` resolves it: `revert`
keeps root Text's boundary and means inherit everywhere else;
`unset`/`inherit` defeat the UA boundary. CascadeBoundary-itest pins
the revert-vs-initial contrast on Views, root Text, nested Text, and
mid-run spans, plus the update path across the two keywords. Bonus:
Text's `viewConfig.uaStyle` entry is gone (the element-catalog uaStyle
machinery remains, for the catalog).

**3. Yoga's enums are codegen and Yoga is its own public API (PR 2).**
`Display.h`/`YGEnums.h` carry `@generated by enums.py` — the PR must
patch the generator, not the output, and `YGDisplay` is public C API
consumed by standalone Yoga users (Litho, yoga-layout on npm) and
synced to facebook/yoga. Also, Yoga does not read RN feature flags;
gating belongs in Yoga's own experimental-feature mechanism, with the
RN flag only controlling whether RN *sets* the style value. Prep:
route PRs 2–5 through the Yoga sync process and flag model, and say so
in each description.

## PR-by-PR

**PR 1 — TextAttributes shrink.** *Ship, one check.* The win is real
and unconditional. Two reviewer questions to pre-answer: (a) the field
reorder breaks any C++20 designated-initializer site (order must match
declaration) — grep upstream + known out-of-tree platforms and state
"none found"; (b) out-of-tree platforms (macOS, Windows) recompile
against these headers — pure recompile, no source break, but tag their
maintainers. The platform-conditioned `static_assert` is the right
shape; keep the comment explaining the size-ordering so the next field
addition doesn't silently regrow it.

**PR 2 — Display enum + flag.** *Prep* (finding 3). Small once routed
correctly; the review risk is process, not code.

**PR 3 — Block layout.** *Prep.* The house verification style for Yoga
layout is **gentest**: HTML fixtures rendered in Chrome generate the
expected values. Block layout is exactly the kind of change that
should arrive with gentest fixtures — the tests are then literally
browser-verified, which converts "do you match CSS?" from a debate
into a diff. Hand-written unit tests alone will draw that request
anyway; preempt it. Also pre-answer the obvious semantic question:
what do flex properties on children of a block container do (answer:
nothing — a block container establishes block, not flex, formatting
context; assert it in tests).

**PR 4 — Margin collapsing.** *Prep.* Same gentest treatment. The
review will probe the classics: negative margins, collapsing through
empty blocks, and the parent-child escape requiring no
border/padding/clearance. The fork's nested-escape rule is right;
fixture-verify each clause of CSS2 §8.3.1 rather than asserting
"CSS2-compliant" in prose.

**PR 5 — Floats.** *Restructure: mark optional and detachable.* This
is where a reviewer's spec-completeness skepticism peaks (floats imply
BFC interactions, clearance, line-box shortening — a long tail), and
nothing later in the sequence depends on it. Declare the implemented
subset precisely, move it to the end of Theme 2, and let it be dropped
without consequence if it stalls. Don't let the hardest 150 lines of
Yoga hold the other 20 PRs hostage.

**PR 6 — `#text` node types.** *Ship.* Unreachable-until-wired with
unit tests is the right stacked shape. One alignment point worth
putting in the description: upstream already models text nodes in its
DOM layer — `ReadOnlyText` exists, `nodeName` `'#text'`, nodeType 3 —
so this PR is the shadow-tree half of an API upstream already shipped,
not a new concept. That framing buys a lot of goodwill.

**PR 7 — `#text` wiring.** *Restructure* (finding 1): re-scope to the
C++ `RawText` intercept in `UIManager::createNode`, no renderer edits;
the true host-config path follows the React sync. Keeping RawText
alive upstream (as the doc already says) is then not just courtesy —
it's the wire protocol until the sync lands.

**PR 8 — Traits + downcasts.** *Prep, and trim.* Add only
`YogaLayoutableKind` and the `asYogaLayoutable()` helper here, with
the profile receipt (RTTI `dynamic_cast` as the top inline-path
sample) in the description — it stands alone as a perf win. The other
five bits (`InlineText`, `InlineReplaced`, `TextCascadeConsumer`,
`SubtreeHasCascadeDependents`, `InheritanceBoundary`) should each land
in the PR that first reads them: trait bits are a finite 32-bit budget
and a reviewer should never approve a bit no code checks. This also
shrinks PR 8 to ~100 lines.

**PR 9 — Inline box props.** *Prep.* Two questions to pre-answer: why
inline margins/borders/padding parse on the text-props side (spans are
text vocabulary; the run fold consumes them), and what the flag-off
parse cost is (now verified zero: the parse is flag-gated, and root
paragraphs skip the inline-box probes entirely — no root paragraph ever
reads them).

**PR 10 — The run node.** *Ship, optionally split once more.* The
clean seam is run model (`AnonymousTextContent` + `InlineElementMetrics`,
pure data + math, trivially unit-testable, ~400 lines) vs the shadow
node class (~500). Worth taking: it removes the sequence's largest PR.
Reviewer focus will be the state shape and the explicit
clone-preserving constructors — the doc comment explaining why
`using ConcreteShadowNode::ConcreteShadowNode` is insufficient must
ride along.

**PR 11 — Run building.** *Prep.* Three things reviewers will drill
on, all answerable: (a) commit-hook ordering — state where the hook
sits relative to existing hooks and why order is safe; (b) the
deferred-rebuild invariant (`yogaChildrenNeedInlineRebuild_` set on
append, resolved in configure, and the append-path visibility rule the
cascade later depends on) — the invariants doc block is the review
artifact, keep it in this diff; (c) out-of-tree exposure —
`YogaLayoutableShadowNode` is subclassed by macOS/Windows components;
tag maintainers. The scaling benchmark riding along is the right call.

**PR 12 — Measure + whitespace.** *Prep.* The subtle reviewer question
is cache correctness: everything that can change fragment rects must
be in the measure-cache key, or stale rects survive prop changes.
State the key composition explicitly. Whitespace tests should cite
css-text-3 section numbers per case — it turns spec review into
checkbox review.

**PR 13 — Paint state + attachments.** *Ship — and lead with the
lazy-state design.* "Every View gains a State" is the make-or-break
objection, and the fork already has the right answer:
`ViewComponentDescriptor::createInitialState` returns `nullptr`, so a
textless View allocates no state object and the pre-feature hot path
is untouched; `updateTextRunStateIfNeeded` performs the lazy
transition. Put that comment in the PR summary, not just the code. The
`documentOrder` interleaving field (CSS painting order vs
all-text-on-top) deserves a sentence too — it preempts the "why not
just draw runs last" simplification a reviewer will suggest.

**PRs 14/15 — iOS/Android mounting.** *Prep.* Fabric-only must be
explicit (Paper untouched — say it and show it). Platform behavior
needs more than Fantom: an RNTester page exercising runs interleaved
with mounted children, plus a manual QA checklist (RTL, font scaling /
`maxFontSizeMultiplier`, accessibility — how do runs surface to
VoiceOver/TalkBack?). Accessibility is the question most likely to be
asked that the sequence doc never mentions; have the answer written
down before the PR opens.

**PRs 16–18 — inline-level display.** *Prep.* `display: 'inline'` is
public API surface: Flow and TypeScript style types, docs, and a
defined flag-off behavior (ignored + dev warning, not silent) belong
in PR 16 itself — type additions are visible to every app even with
the flag off, so reviewers treat them as the real API review. PR 17's
baseline-alignment rules should cite the css-inline-3 model it
implements; PR 18 is small enough to fold into 16 if review bandwidth
is scarce.

**PR 19 — Inheritable props.** *Prep.* The guaranteed objection: "why
eleven inline `std::optional` fields (+68 B on every ViewProps) instead
of one pointer (+8 B) to a lazily-allocated struct?" The honest answer —
boxing adds an allocation + indirection per *styled* View and
complicates parse, and the fork chose measured inline cost with the
ledger published — must be in the PR description with the numbers,
alongside the `hasInheritedTextProps` bit that makes the common case
one-bool cheap. If the reviewer still prefers boxing, that's a
legitimate design conversation to have *in this PR* — which is exactly
why the fields land inert and alone.

**PR 20 — The cascade, complete.** *Ship — this is the sequence's best
PR now.* Correct-and-fast in one review, benchmark parity rows as
proof, invariants doc block as the review artifact. Two things to
pre-answer: (a) the two added virtuals on `YogaLayoutableShadowNode`
(`setInheritedCascade`/`getStoredCascade`) — vtable dispatch on a hot
class; the answer is they're called only on trait-gated consumer
paths, never in the common no-text walk; (b) reparenting correctness —
the `receivedTextAttributes_` memo is load-bearing for reparented
subtrees, and the regression test that caught the grandparent-cascade
bug should be named in the description.

**PR 21 — `all` boundaries.** *Restructure* (finding 2): fix `revert`
semantics for the no-UA-origin world before it ships, inside this PR.
Everything else is right, including expressing root `<Text>`'s
boundary as a trait default cleared by authored `all: 'unset'` — and
the description should note the deliberate scope: `all` here covers
the inherited text set because those are the only cascading properties
this renderer has (css-cascade-4 §3.2 excludes `direction`/
`unicode-bidi`, which RN doesn't cascade anyway).

**Theme 8 — geometry + events.** *Prep.* Wire into the existing DOM
layer rather than beside it: `ReadOnlyText` already exists upstream,
so fragment-rect `getBoundingClientRect` should surface through the
standard `ReadOnlyNode`/`ReadOnlyText` APIs, not a parallel
entrypoint. Pointer events resolving to fragment emitters will get a
hit-testing review — the fork's rule (fragment rects in run space,
document-order resolution) needs its tests riding along.

## Cross-cutting prep (applies to most PRs)

- **CI honesty:** the benchmark suites run as ordinary 1-iteration
  Fantom tests in CI unless `FANTOM_RUN_BENCHMARKS=1`; they are
  regression *smoke*, not regression *measurement*, in upstream CI.
  Say so rather than implying CI enforces the numbers.
- **Out-of-tree platforms:** PRs 1, 11, 13, 20 touch classes
  subclassed by macOS/Windows/visionOS. Tag maintainers proactively;
  their breakage reports arriving post-merge is how sequences stall.
- **Changelogs:** every PR needs the RN changelog block; the
  flag-gated ones should say "no behavior change with
  `enableStringChildren` off" as the first line — it's the sentence
  reviewers look for.
